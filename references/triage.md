# 红三分诊手册（Triage Playbook）

巡查中每一个「红」（测试失败、构建失败、线上异常、扫描器报警）在动手前必须走完本手册。三个问题按顺序回答，**顺序不能换**——跳过「它是真的吗」直接修，是巡查事故的第一大来源。

---

## 问题一：它是真的吗？（现场定性）

### 1.1 先怀疑树，再怀疑代码

共享工作树上的失败，第一嫌疑人是现场：

- 并行会话的未提交改动（工作树漂移）
- staged 残留/陈旧副本（内容 != 提交树）
- 上一次构建的脏产物

**判例：体检红先验工作树==origin 再定回归。** 「体检绿只证明树上的测试」——树上不是正典基线时，红与绿都不携带关于代码库的信息。

**可靠形态：origin 隔离 worktree。** 共享树有手术态（staged 删除、未提交改动）时，不要试图甄别每一个文件，直接以远端基线建 worktree 跑体检：

```bash
git fetch origin
git worktree add /path/to/wt_audit <origin基线commit>
# 依赖重的项目把 node_modules 链接进去（Windows: mklink /J；Unix: ln -s）
cd /path/to/wt_audit && npm install 或复用链接
```

worktree 内容==提交树后，假红源被结构性消除，甄别成本从「逐文件对拍」降为零。

### 1.2 「M 态」≠ 在制

`git status` 里的 M（modified）只说明文件与索引不同。它可能是：活跃在制、陈旧回退残渣、或并行会话的手术态。**不能只凭 M 态决定让位或动手**，用双证据定性：

1. **内容对拍**：`git diff origin/main -- <file>` 看工作树相对基线缺什么/多什么。若把已上线的内容整块删掉，这不是「在写新功能」的形状。
2. **mtime**：文件最近修改时间。冷了十几小时的 M 态基本是残渣；几分钟前的才是活跃在制。

**判例：「文件是 M 态」≠「有人在制」**——凭 M 态连续多轮让位，会把真缺口一直判缓下去（真实事故：同一文件四轮「在制让位」，最后一查是陈旧回退残渣）。

### 1.3 负载型 flake 的完整甄别协议

全量测试两跑红数不一致时的三级协议：

```
第一级：两跑取文件级并集
   → 红数波动大（如 13→16 文件）恰恰说明采样不稳，方向是 flake
第二级：并集内每个文件单独跑
   → 单跑绿 = 该文件在全量负载下才红，负载型 flake 实锤
   → 单跑仍红且两跑均红 = 疑似确定性回归，进问题二
第三级：并集文件并批复跑（模拟中等负载）
   → 并批红 = 完整复现闭环；并批绿 = 记录为「饱和 flake」留观察
```

**判例：红数绝对值不携带定性信息，文件级并集才携带。** 不要因为「今天红了 32 个用例」就恐慌，也不要因为「只红了 5 个」就放过。

**留观察规则**：同一文件在多轮巡查的两跑并集中稳定出现 ≥3 轮，从「flake 留观察」升级为「立项治理」（如给真实时钟的测试做 mock 时钟改造）。flake 集中区往往是真实钟+轮询+网络 mock 的重活户，值得点名观察。

### 1.4 跨日伪红

时间相关测试的 fixture 写死日期（如 `2026-09-21`），组件按「过去时」过滤——日期一过期，fixture 全灭，表现为与代码无关的批量红。**修复范式 = fixture 相对化**（`ymd(offset)` 生成相对日期），或断言时手算未来锚点。凡涉及日期/时间窗口的测试，巡查分诊时先查 fixture 日期是否已过期，再查代码。

**判例：跨日伪红第 N 度应验**——同一批测试连续多轮「神秘红」，罪魁是三天前写死的日期。now 注入参数第一天就应进函数签名，别等伪红教做人。

### 1.5 gate 绿 ≠ 浏览器绿

构建门禁用的是解析器（postcss/esbuild/bundler），解析器有容忍度；运行时（浏览器/Node）语义更严格。真实事故：CSS 缺一个右括号，postcss 按嵌套语法容忍解析，构建全绿，浏览器却把后续所有规则吞成死规则。**结论：解析型门禁之外，按仓库形态保留一层真实运行验证**（浏览器打开、CSSOM 检查、端到端冒烟），尤其当本轮改动是「救场」性质时。

### 1.6 工具本身也是嫌疑人

扫描器/脚本报警时，先问：**这个工具上一次被验证是什么时候？**

- **判例：「跑过」≠「提交的版本跑过」**——上次跑的是工作树版本，入库 blob 从未烟测，一跑 ReferenceError。工具入库前必须以入库形态（干净检出或 `git show` 出的内容）烟测一次。
- 扫描器的「死候选」名单整体不可信的案例真实存在（注释剥离 bug 导致行号错位）。**扫描器单源不可作删除依据**，删除令必须过独立复核。
- 断言谓词比设计容差更严 → 稳定假红（「断言域与设计容差对齐」判例）。

## 问题二：它是谁的？（归属定性）

确认红是真的之后，五桶归类：

| 桶 | 判定 | 处置 |
| --- | --- | --- |
| **在制不代管** | 红来自并行会话未落库的文件（?? 或活跃 M 态） | 不碰、不修、不接线，等它落库后按新债分诊 |
| **他方已落库债** | 红在已提交代码里，但归属其他工作流（如某功能域的既有测试债） | 记档归入对应域的清单；若连续多轮出现，触发复检（见 2.1） |
| **我方回归** | 红由本工作流最近的改动引入 | 立即修复，这是巡查的当前义务 |
| **flake** | 过了 1.3 的完整甄别 | 留观察并记复检触发条件 |
| **陈旧测试** | 代码行为已按新口径演进，测试还在断言旧行为 | 更新断言并注记演进原因；先确认新口径确实是「演进」而非「回归」 |

**「我方」的判定要靠证据不靠感觉**：红文件的最后落点提交是谁、哪个工作流碰过它。零触碰实证（红文件最后提交远早于本工作流起点）是自证清白的硬证据。

### 2.1 归档清单会过期

**判例：自愈意味着归档清单过期。** 「连续四轮红」的旧债，重查时可能已经自愈（依赖升级/并行修复）；反之，当时判缓的理由（「宿主文件活跃」）也可能已不成立。规则：

- 归档项带复检触发条件（时间窗/出现次数/前置条件变化）。
- 「存量形态挂两次就该重估」——挂起是当时不划算，不是永远不划算；被点名第二次 = 复检触发条件满足。
- 复检的期望收益高、动作便宜（重跑+读 diff），始终值得做。

## 问题三：要不要现在修？（处置）

只有两桶进修复：**我方回归**、**确认的真缺陷**（他方债若正在造成面上阻塞且无人认领，经定性后也可修，但要在报告里写明归属变迁）。

### 3.1 修复纪律

- **完整链先行**：先写清缺陷链（入口→传播→后果），再决定堵哪一环。只堵观察到的入口不叫修复，叫打地鼠；堵完一个环，**同链其他入口排查一遍**。
- **红=三种病，修法不同**：
  - 测试错（fixture 过期/环境依赖/断言过严）→ 修测试；
  - 产品错（功能真坏了/只写不读/承诺无出口）→ 修产品；
  - 断言陈旧（行为按新口径合法演进）→ 更新断言并注记。
  **定性错了会把好代码改坏**——把「测试错」当「产品错」修，会为迁就坏测试扭曲正确实现。
- **测试进闸**：修复同步补测试，且测试命名/位置纳入仓库既有的门禁收集机制，让闸以后自动拦同类回归，而不是依赖下个人记得。
- **诚实边界**：修不了/不该修的，写明原因归档，不假装修了。

### 3.2 什么不修

- **噪声源驱动，不为洁癖翻热文件**：卸载后 setState 无害 no-op 这类「理论上不干净」，批量修 10 个热文件的 churn > 收益时不动。噪声源（产生测试噪声/日志噪声的）优先，纯洁癖靠后。
- **「修复」不得引入新耦合**：为消除一个 warning 而给热文件加跨域 import，通常是负收益。
- **删除令三重验证**：扫描器说可删 ≠ 可删。独立复核 + 双工具对拍 + 完整性断言（删完后断言应保留的标记仍在），完整性断言是最后防线。

### 3.3 报告与判例

修复/分诊完成后：

- 每个定性结论写进报告（分诊表：红 → 桶 → 证据 → 处置）。
- 本轮新学到的判断规则写成**判例**（一句话规则 + 为什么 + 怎么应用）。判例是巡查体系的复利载体——下期对账时，判例清单就是「已踩过的坑」。
- 翻车更要入库：「本轮第一版把 X 误判为 Y，因为 Z」比十条正确判断更有保存价值。
